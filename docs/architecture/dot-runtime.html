Where Dot’s capabilities come from—and where they stop

The main bottleneck is the execution system around the LLM: which tools Dot exposes, how long it lets a task run, and whether the result tells the model what actually happened.

The same reasoning model can perform very differently when one app supplies an editable workspace, terminal, feedback and a persistent tool loop, while another exposes a smaller set of actions. A model response alone cannot move a pointer or inspect a running process.

2. Why Mouse Mover could say “success” and then stop

Two recorded starts were followed by native helper reconnects about 600 milliseconds later. A controlled test reproduced pointer/command starvation using slow simulated macOS Accessibility work. That establishes a failure mechanism consistent with the timing; the original logs do not identify which app’s Accessibility call stalled.

There was also a separate voice-routing failure: the installed local Qwen router classified a greeting followed by a request to move the mouse as casual chat. That path can speak but does not execute tools. The revised routing prompt passed all 13 added Ability cases and improved the 70-case local evaluation from 63 to 68 correct decisions, with no regressions. Two ambiguous, non-delegating classifications remain. Free conversation can still invent action claims if a future request is misrouted; the prompt correction is not a general guarantee of grounded replies.

3. Why folder selection seemed stuck

The affected saved request had no selected folder. An isolated regression reproduced selection loss during approval-feed refresh. The real native picker then successfully selected a test folder with approval still pending. This verifies the selection path without granting access to owner files.

4. Why Dot does not currently behave like Codex

Capability Dot’s pre-Codex implementation Codex-style development workflow
Reasoning Configured subscription model through Integrator; High voice also has a smaller local routing/conversation model. A coding model works within a runtime that can inspect, edit, execute and verify.
Local execution Integrator explicitly disables native CLI shell, browser, plugins and tool execution. Dot executes only its exposed application tools. Available tools can run commands and patches in an authorized workspace under configured sandbox and approval rules.
Code debugging Folder grants allow bounded file reads/writes. They do not grant host shell, process attachment, test execution or app rebuilds. An optional isolated computer has its own shell. Read source → reproduce → change → run checks → inspect failures → repeat, when the environment supplies these tools.
Self-diagnosis This fix adds inspect_dot_runtime: current Dot/conversation only, host connectivity, enabled abilities and safe recent receipts. Ability status supplies live activity state and stop reason. Tool outputs, terminal logs and execution feedback support deeper diagnosis.
Persistence / limits Saved conversations and memory exist, but individual tool turns are bounded. Background voice tasks are separate linked conversations. Tool results and context are bounded. The harness manages longer work, context, tool interactions, progress and recovery; actual limits depend on configuration.
Permissions Separate grants for folders, Abilities, connected apps and isolated computers. Choosing a path is not approval. Sandbox and approval controls still apply. More capable execution does not mean unrestricted access.

To make Dot a general development agent, it would need an explicit development workspace and command/test runner, durable task continuation, diagnostic access and reliable tool evidence. Turning off permission checks or merely switching the LLM would not provide those pieces.

The fixes here improve the existing bounded runtime. They do not add unrestricted host shell access, automatic app self-modification or a full Codex runtime.
