# Dot agent reliability postmortem

25 October 2026 · Draft for discussion · Owner and implementing assistant

Dot’s reliability problem extends beyond Mouse Mover. The strongest explanation is that we have assembled substantial individual capabilities without consistently proving that they work together as one agent. Different conversation paths make different decisions, execution results do not always establish the user’s intended outcome, and recovery across permissions, tasks and native processes remains uneven. Our verification and delivery process has allowed those gaps to reach everyday use.

That is an engineering and product-readiness problem. Some failures involve the local model; several others occur before inference or entirely outside the LLM. The evidence does not support blaming an unclear request, a single library, or the user for the overall experience. It also does not establish that changing the model or rewriting the stack would solve it.

## Scope and impact

This review covers the recurring agent failures documented from 18–25 October: conversation quality, voice delegation, context capacity, tool selection, task continuation, result reporting, permissions, native execution and updates. Earlier incidents are assessed from their recorded investigations and current source; they were not all reproduced again for this postmortem.

The observed impact is repeated owner intervention, interrupted testing, actions that did not match the reply, and difficulty knowing whether to retry. A false success is particularly damaging: it undermines confidence in later correct replies and can make retrying a consequential action unsafe. A permission denial is legitimate, but an unexplained “setup needed” leaves the owner doing the diagnosis.

These records concern a development installation and selected test cases. They do not provide an overall task-success rate, production availability figure, or statistical ranking of which subsystem fails most often. They also do not establish a general memory-quality problem or data corruption. Those should be measured separately rather than added to the incident list by assumption.

## Root causes across the agent

### One Dot presents several different execution paths

Text and Basic/Medium local voice use the main task agent. High voice adds local recognition, routing and conversation, with tasks delegated into linked conversations. It also supplies a bounded recent-history view, while the main agent assembles a different context and tool set. The same persona therefore masks differences in reasoning, context and execution.

The routing failure, missing voice Ability admission recorded in earlier work, and completed-task continuation failure all occurred at these boundaries. Separate paths are not inherently wrong, but their behavior was not consistently equivalent from the owner’s perspective. The product promises continuity more strongly than the implementation currently demonstrates. [Voice runtime](../../src/server/local-voice/native-runtime.ts), [voice tool repair](../desktop/abilities-verification.md#voice-tools-volume-restoration-and-markdown-october-24-2026)

### Technical validity was stronger than task correctness

Dot has meaningful validation: permitted tool names, structured arguments, scoped grants, worker boundaries and persisted receipts. Those checks can establish that an invocation is allowed and well formed. They cannot establish that searching again is the right continuation, that a task was actually delegated, or that a cursor is still moving.

Some important behavior was left to prose instructions: when to delegate, which tool to resume, and when a reply may claim success. The Spotify selection instruction and High routing probes demonstrate the risk. The missing activity feedback made it harder even for a capable model to correct itself. The cross-cutting gap is a consistent relationship between **requested action, execution state, observed effect and reported outcome**. [Subscription contract](../../src/server/subscription-prompt.ts), [decision validation](../../src/server/subscription-adapter.ts)

### Readiness and self-diagnosis stop short of the actual action

An Ability can be installed and enabled while its desktop host, selected Dot, OS permission or native helper is unavailable. The recent diagnostic tool reports useful configuration and historical receipts, but it does not yet expose every action prerequisite. The latest `setup_needed` reply was truthful about failure and still insufficient for recovery; I had to inspect desktop health outside Dot to identify Accessibility.

The same distinction applies to debugging. Dot does not inherit this development assistant’s terminal, source checkout or tools. The subscription integration asks the provider for decisions; Dot executes its own allowed tools. Local folder access permits bounded file operations, not a host command/test runner. The normal agent loop defaults to five model iterations, with ten for specified configurations, and a configurable 90-second turn deadline. These are capability constraints, not proven causes of every incident. Better reasoning cannot compensate for missing evidence or an unavailable execution tool. [Agent loop](../../src/server/dot-agent.ts), [timeout configuration](../../src/server/platform-config.ts), [architecture](../architecture/dot-runtime.html#limits)

### Testing favored individual boundaries over complete user journeys

The tests and reviews did catch real defects. The gap was what remained outside their assertions: real model behavior, actual native object destruction, OS permission changes after a rebuild, and sequences spanning voice, approval, action, follow-up and restart.

For example, a JavaScript test double kept `webContents` accessible after “destruction”; the actual Electron accessor threw. A simulated pointer established host/protocol behavior without proving sustained physical movement. Router examples used during prompt tuning established regressions, not independent generalization. High passed plumbing checks before failing ordinary conversation. Test volume was not the missing ingredient; representative outcomes and release gates were.

Existing verification documents often stated these limits accurately. The process failure was allowing documented outstanding acceptance to remain outstanding while capabilities and ordinary owner testing continued to expand. The latest running build was handed over after checking its window and workspace connection, without checking the Accessibility prerequisite of the feature the owner was about to test.

### Delivery and recovery were treated as secondary behavior

The project has several worktrees, packaged app locations and optional runtime configurations. Isolation protects concurrent work, but there was no single candidate identity visible to the owner tying source, package, models, Ability versions, workspace and permissions together.

The packaging script explicitly identifies ad-hoc signing as a mode in which permission renewal may be required. The earlier Spotify incident had already demonstrated that an enabled old Accessibility entry could be misleading. I still failed to make that check part of this handoff. Native startup, shutdown, upgrade and recovery need to be part of feature acceptance, not chores performed after the feature has passed. [Signing behavior](../../scripts/sign-desktop.mjs), [earlier permission incident](../desktop/abilities-verification.md#spotify-permissions-and-selection-continuation--october-23-2026)

## Fair allocation of responsibility

**The engineering and verification process carries the primary responsibility for letting these failures reach routine use.** In this session, I own the incomplete verification and handoff. I should have checked the complete request-to-effect chain, verified action prerequisites before handoff, and caught real native teardown behavior. I built a second package before the follow-up lifecycle investigation was complete, which added rework. During permission repair I also spent time on a UI selection that looked selected but had not enabled removal. Those execution mistakes prolonged the interruption.

The two shutdown defects were already present at the base commit, before the current uncommitted repair. It would be inaccurate to say this repair introduced them. It is accurate to say I failed to detect them in the repair’s earlier verification. Independent review did not remove that responsibility. [Baseline code and check results](2026-10-25-agent-reliability-evidence.json)

**Your requirements were clear enough for the basic behaviors that failed.** “Move my mouse,” use the chosen folder, continue a chat and do not claim an action happened when it did not are reasonable expectations. You did not need to specify Electron destruction semantics, prompt headroom or macOS code identity. I found no evidence that you directed us to skip these checks.

There is a genuine product decision to clarify together: whether Dot is currently an experimental companion, a dependable task assistant, or a development agent expected to inspect, reproduce, edit and test its own code. Those imply different tools and acceptance standards. The broad feature scope and accepted local-voice tradeoffs increased the work required. They do not explain away incorrect success claims or broken basic workflows. Your main influence on prevention is prioritizing a smaller reliable baseline and agreeing on the experimental boundary; my job is to make those tradeoffs concrete before building.

**The stack adds integration cost, but a stack-wide defect is not established.** React/CopilotKit, TanStack/AG-UI, the subscription adapter, Electron, Swift helpers, Python speech and storage cross several process and state boundaries. The observed failures predominantly sit in our orchestration, instructions, resource budgets, lifecycle handling and delivery checks. Replacing a framework would not automatically fix those contracts. The local model does have demonstrated routing/grounding weaknesses; that finding should not be generalized to every LLM or every Dot request.

Raising the context limit, adding prompt examples or switching models can be useful repairs. None substitutes for an explicit supported baseline, trustworthy outcome reporting and end-to-end acceptance. A full rewrite is not justified by the evidence collected so far; targeted simplification should be evaluated against the same user journeys.

## Questions for our discussion

**Owner response recorded on 25 October:** correct folder permission, dependable installed Abilities and full project debugging are the stabilization baseline. High voice is central to the product vision. Debugging includes runtime diagnosis, approved source inspection, edits and test execution. Speech must stay local, and the companion must not require an additional subscription beyond a supported AI subscription the user already has. See [requirements, development rules and automation status](../development/agent-reliability.md). The original questions below are retained as the discussion record; Codex-first execution with local speech was subsequently approved and implemented. Measurable acceptance thresholds remain open.

1. Which few tasks must Dot perform dependably before we resume adding features?
2. Should High local conversation remain experimental until it meets the same action and recovery standard as text, even if a common task path is slower?
3. What should “Dot can debug itself” mean initially: explain runtime failures, inspect an approved source folder, or also edit code and run tests in an explicitly configured development workspace?

The central decision is the reliability standard for the next milestone. Once that is agreed, we can choose the smallest changes that meet it and judge them by repeatable outcomes.

## Implemented follow-through — 25 October 2026

The approved Codex-first candidate now has one execution path for text and High voice, explicit folder execution grants, durable queue/cancellation state, host-owned Ability outcomes and local LFM recognition with macOS Samantha speech. The original “LLM access means coding capability” assumption was replaced by an actual scoped execution-session integration. Failed execution cannot become an unconditional completion receipt.

Development checks now include a full core profile with a dedicated test database, native macOS acceptance, packaged-runtime checks, build identity and documented live journey qualification. Repository instructions require semantic review of observed effects, exact permission targets and regression coverage of failures. The final qualification also exposed weak single-example tests and an unbounded synthetic input generator; stronger contracts and bounded fixture processes are recorded in the development rules. This prevents declaring success merely because the test harness returned green.

See the [qualification record](../development/codex-execution-qualification.md) and [owner test guide](../development/codex-test-handoff.md) for measured results, retained failures, recovery and the remaining physical-device acceptance. This candidate improves the architecture and failure evidence; it does not establish universal task reliability.

### Post-handoff schema failure

Owner testing exposed `Transforms cannot be represented in JSON Schema`. The Codex adapter exported Zod output schemas although the provider supplies inputs. The desktop website tool normalizes URLs with a transform; registering that tool therefore failed before inference, even for an unrelated message. The previous live matrix omitted the desktop browser callback, and the packaged startup smoke did not send an agent request. This was an implementation and qualification gap, not an unclear owner requirement.

The correction exports input schemas and retains host parsing before execution. New failing-then-passing regressions cover the actual desktop tool schema, unsafe URL rejection, normalization, and ordinary text/voice through real storage. Live task qualification now registers the browser tool with explicit refusal of external effects. Catalog parity is documented as a future development rule. The source correction is small; its significance is the missing configuration boundary in the earlier evidence.

### Post-handoff voice conversation regression

The owner heard and saw only “Received” after ordinary utterances. The Codex-first runtime deliberately synthesized that fixed acknowledgement for every accepted turn, including casual conversation. Actual answers completed asynchronously, but the call transcript recorded only the immediate acknowledgement. Some answers completed after the owner ended the call. A result from an earlier task could also reach a newly starting call before its local worker finished warming, making a concurrent synthesis request fail and ending the call. These are implementation and acceptance gaps; the owner had already made natural voice conversation a core requirement.

The correction removes spoken admission acknowledgements and empty assistant history messages, waits silently for the real answer, records that answer in the call transcript, and defers result speech until the worker is ready. Explicit status/stop questions and actionable blockers still receive replies. Regression tests reproduce the transcript omission and warmup race before the correction.

Two limits remain distinct. First, the reliability implementation selected fixed Samantha speech after the previous generative engine repeatedly failed to finish synthesis. That improved bounded completion but reduced expression; removing acknowledgements does not restore emotional prosody. Second, software playback acknowledgements do not prove that the owner heard the words. Twelve synthetic production-worker roundtrips recovered the intended words at the correct rate, but a separate injected-latency probe demonstrated playback gaps when per-frame permission checks took longer than the audio frames. Actual owner storage latency and physical playback were not measured, so this does not establish the cause of every unheard reply. Permission revocation checks remain intact.

Future voice acceptance must include ordinary greeting, thanks, follow-up, slow response, interruption and a result arriving during call startup. Check substantive answer text, persisted call transcript, audio content and elapsed time separately. Retain a human listening gate for audibility, timing and expression. Local task execution reliability and a pleasant conversation are both required; one cannot stand in for the other.
